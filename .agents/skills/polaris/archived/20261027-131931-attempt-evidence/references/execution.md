# 实现、执行与报告

## 输入与授权

先完整读取 [Scenario Acceptance 工作约束](scenario_acceptance_spec.md)，再读取已确认业务设计、Acceptance Cases、Technical Design 和 Automated Acceptance Plan。按 [任务入口](modes.md) 确认本轮是否允许修改业务行为。

已有范围、Case 与实施计划授权后直接实施，不重新生成大型 Roadmap，不逐步骤等待批准。只有产品决定、计划外改动或关键阻塞才暂停相关工作。

## Implementation 与 Case Runner

只实现当前约定范围，遵循已确认模型、状态规则和接口，复用项目能力。新开发与增量模式允许自主编码、调试、必要的局部重构和测试；补建验收原则上只实现 Runner 与已获准的测试接入。

代码与场景测试同步推进。采用项目选定的测试框架，Runner 使用计划中的独立验收集合与运行入口，不混入单元测试。

每个场景测试具有业务名称与 Case ID，代码清楚区分 Given、When、Result、Expected，保持独立业务断言和可定位的失败说明。用局部命名、结构或必要的摘要注释表达，不堆砌复述代码的注释，不造巨型通用解释器和隐式断言。

严格按计划从真实业务入口执行、运行核心逻辑、观察最终状态、必要副作用与禁止行为。不得只检查成功返回，不用单元测试替代完整业务场景验收。补齐 [Case 到 Runner 的映射](cases.md)，测试位置与运行入口必须实际可用。

## Evaluation 与修复

先实际运行，再写 Result。失败后读输出，形成原因假设，用最小实验验证，再修根因。测试定位器或 Fixture 错误可修，但保留业务断言并说明变化。不得修改已确认 Expected、削弱断言或绕过核心逻辑。

新开发与增量模式修复本轮实现问题后重跑相关 Case 及必要回归；补建验收发现真实业务缺陷保留 FAIL 并登记，不擅自修业务代码。预期争议回到审核，环境与 Runner 错误修复后重跑。

环境不可用、外部服务异常、需求冲突，或同一原因重复失败而无新证据时，停止无意义重试，保留输出并说明恢复条件。不能通过删除失败 Case、跳过或降低 Expected 获得绿色结果。

## 执行证据

每批次写入当前工作目录的独立证据位置，保留原始失败与后续重跑。记录执行时间、实际命令或入口、Case 版本、代码版本及相关未提交差异、Runner 版本、环境、真实依赖与 Mock 边界。

没有 Git 时用内容摘要等可复核标识，不伪造提交号。根据验证需要保留日志、Trace、截图或测试报告，不要求每种都有；脱敏后仍应足以复核结论。

版本、Expected 或边界变化后旧结果不能证明新版本通过。状态记录只是索引，必须能追到实际证据。

## Evaluation Report

输出本轮能力与范围、Acceptance Coverage Matrix、关键证据、真实依赖和 Mock 边界，以及未完成、未覆盖、需要人工验证的事项。逐 Case 记录 ID、对应测试、业务验证内容、实际观察、状态、证据位置与未验证边界。

状态定义：
- PASS：本版 Case 的全部必需断言和核查项已执行并通过。
- FAIL：有效执行后观察到违反已确认 Expected 的业务行为。
- ERROR：环境、Fixture 或 Runner 错误使执行无法有效完成。
- INCONCLUSIVE：证据不足或语义判断无法可靠得出结论。
- NOT_COVERED：尚无对应验证，或本批次未执行，包括跳过的测试。

一个 Case 有多个测试或人工核查项时逐项列出，全部通过才记 PASS，不能用绿色汇总掩盖部分执行。退出码只说明进程结果，还要逐 Case 核对业务断言、观察与覆盖。

## 完成条件与下一步

新开发与增量模式：本轮必需 Case 均实际执行并通过，有可追溯证据；增量同时验证受影响旧行为。未达到就报告剩余问题，不以编译成功、单测通过或自我判断宣称交付完成。

补建验收模式：约定范围形成已确认 Case、真实执行记录、清楚的覆盖与遗留问题。允许保留已知业务 FAIL，但与已通过回归基线分开；环境阻塞、未执行和争议不得冒充已完成验收，也不能把补建工作完成说成产品通过。

批次结束先回到父级业务切片核对结果。只有内部能力通过时，记录该能力和剩余集成路径，不作父级接受决定；继续拆分前按工作记录中的长任务接续规则检查推进方向。项目要求流程迭代时，此处同时复查实际使用暴露的流程问题，按项目权限和归档规则处理，不能把“使用了skill”本身当作流程有效的证据。

按需更新 `evaluation.md`、Case 映射和 `state.md`，产品接受由用户或其明确授权的主持者决定，保留决定归属与验收证据。随后读取 [人工体验](experience.md)；补建模式按需要补充人工业务核查，不强制一套新功能体验流程。
