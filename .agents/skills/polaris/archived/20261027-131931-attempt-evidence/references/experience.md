# 人工体验与交付决定

## 输入与目标

读取当前需求、业务设计、Acceptance Cases 与 Evaluation Report。新开发体验当前切片，增量按变更影响体验新增与相关旧路径，补建验收按需要安排人工业务核查。

人工体验判断产品是否自然、值得使用，也能发现设计遗漏。不要把自动化 Case 逐条转成人工检查清单。没有 UI 的系统也可以通过真实业务输入、对话和结果进行体验。

## 授权体验

默认由用户自由体验并作接受决定；已有明确代理授权时，由受托主持者安排真实产品体验和作出决定，记录授权来源、实际操作者、方法、证据及能力边界。下文“用户决定”按该授权执行，但不能把Agent体验标成人类体验，不能免除必需Case或用主观接受覆盖失败。若要求必须依赖真实人类反馈且尚无证据，保持未验证并推进其它可执行工作。

## 准备

说明已实现能力、如何启动和重置、体验数据、已验证及未验证边界。能由 Agent 准备的环境与数据先准备好；无法准备的如实说明。

根据当前范围生成 2～4 张由 AI 撰写、供人使用的任务卡。每张包括 Mission ID、名称、用户背景、任务目标、关注点和完成判断。不规定点击路线，不由 Agent 代替用户执行后宣称已完成人工体验。小任务可减少卡片数量并说明原因。

用户按目标自由操作，也可自由探索。设计阶段可用原型提前体验；工程验收后体验真实产物，两个结论分别记录。

## 接收散装反馈

接受自然语言、截图、录屏、操作过程和主观感受，不要求用户套模板。一个明确问题或改进点对应一条反馈：

- Feedback ID、标题、来源 Mission ID 或自由探索。
- 主分类与关联类别：实现缺陷、自动化验收遗漏、产品体验问题、新需求或设计变化。
- 原始反馈：保留用户关键描述。
- 实际观察：明确是用户报告、Agent 实测还是推断。
- 期望行为：引用已确认规则，或标注待确认。
- 证据位置、影响程度、建议处理及处理状态。

按项目已有优先级定义标注影响；没有定义时先描述影响，再给待确认的优先级建议，不凭情绪自动标为最高级。信息不足标待确认，只询问会影响判断的歧义。截图不能证明看不到的操作或状态。

同一问题可关联多个类别，明确主处理方向。例如实现缺陷同时暴露验收遗漏时，关联修复与补 Case 两项行动，不修完代码就关闭全部反馈。

## 分流与决定

实现缺陷：指出违反的已确认规则，提出修复与回归建议。
验收遗漏：指出缺失 Case、失效 Oracle 或未观察到的副作用。
体验问题：功能可能符合设计，提出改进方案供人判断。
新需求：说明与当前范围关系，等待选择本轮变更或后续规划。

反馈独立于 Case。只有预期已确认且具备判定方法的事项才转为正式 Case；不得把抱怨自动当成新业务规则。

结束时输出实际完成的体验任务及结果、独立 Feedback Records、按四类汇总的 Feedback Summary、Follow-up Actions，以及 Acceptance Recommendation。建议可以是 Accept（接受）、Accept with Follow-ups（接受并跟进）或 Rework（返工），说明理由，由用户决定。没有相应授权时，不得代写接受决定；有明确授权时按“授权体验”记录受托决定。

自动化结果与人工体验决定分别记录。必需验收未通过或仍有阻断缺陷时不能用“有条件接受”掩盖；若需缩小交付范围，必须明确重新审核范围和预期。非阻断的新想法不自动阻止当前工作结束。

## 产出与完成条件

保持记录轻量、清晰、可阅读，不生成冗长的测试报告；只保留判断问题、作出决定和接续工作需要的信息。

按需将任务卡、反馈和总结保存在当前工作目录，更新 `state.md` 中的实际体验、用户决定及未完成事项。用户选择返工就按获准范围修复并回归；涉及新需求或规则变化则先回到需求与业务讨论，不直接改 Expected。

完成条件：实际体验或人工业务核查有记录，反馈已分类，用户作出本轮决定，后续行动明确。没有进行体验就写未进行。将获准的后续需求纳入下一轮切片，使反馈回到产品设计。
