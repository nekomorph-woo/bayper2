# 需求与 PRD

## 输入与目标

先按 [任务入口](modes.md) 识别模式，再整理业务依据。输入可以是想法、已有 PRD、用户反馈、现有代码或业务资料。已有确认材料直接复用；缺少文档不等于缺少需求，也不等于必须先写一份大型 PRD。

本阶段回答：为谁解决什么问题，应该具备什么业务能力，哪些属于本轮讨论范围。这里建立全局业务模型骨架，选定切片后再细化局部规则；不设计数据库、API 或模块。

## 从零开发：Idea → PRD

与用户探索产品愿景、目标用户、使用情境和核心问题。先提出理解与建议，再针对会影响产品方向的未知提问，不一次抛出完整问卷。

讨论并确认：
- 产品价值与成功判断：用户完成什么任务，什么结果说明问题已解决。
- 核心业务能力与端到端用户路径；产品边界与暂不做的事项。
- 全局业务对象及其关系、主要生命周期、用户与 Agent 各自可执行的行为。
- 影响产品形态的约束、假设、风险和待决定问题。

产出精简 PRD，保留已确认决定与待验证假设的区别。不要用实现细节填补产品问题，也不要把局部属性、所有异常分支提前设计完。

完成条件：用户认可产品方向、核心范围和全局模型；未解决问题不妨碍选择下一条价值切片。接着读 [切片与场景范围](slices.md)，由用户选择本轮切片。

## 增量开发：新增需求 + 旧系统理解

从本轮新增或变化的需求开始，沿现有业务入口读代码、业务模型、Case、数据和关键路径，确认哪些基线已实际运行、哪些仅由阅读推断。旧 PRD 与代码冲突时分别记录，不自动认定任何一方正确。

结合现状讨论：新增价值、原有对象与状态如何复用、哪些行为必须保持、历史数据与接口的兼容约束，以及变化影响的用户路径。

产出简短增量需求与变更影响摘要：
- 本轮新增或改变的业务行为及明确排除项。
- 复用的对象、状态、接口与不能破坏的旧行为。
- 受影响的既有 Case，以及重要但缺少保护的旧行为。
- 文档与实现差异、待确认产品决定及风险。

已有 PRD 可引用，只记录本轮增量；没有 PRD 时整理够本轮判断的需求，不重建全产品文档。

完成条件：本轮需求、兼容约束和影响范围已确认，足以选择切片。明确的小 Bug 可引用已确认 Expected 直接走修复与回归，不强制重新写 PRD。

## 补建验收：从现状还原业务预期

不设计新产品。收集业务资料、历史需求与缺陷记录，结合代码、已有测试及可观察使用行为，识别已有系统的业务承诺。

先整理场景清单，分别记录业务能力、实际行为、依据与未知项。代码只说明当前实现，不能单独决定正确预期。区分已确认正确、正确性未确认、已知违反业务预期三种情况。

产出业务预期摘要与初步场景清单；没有 PRD 时允许用这些材料替代，不补造一个“已确认 PRD”。先与用户选定值得保护的业务范围，再讨论其中的规则与 Expected，最后展开 Case。

完成条件：能区分已知事实、阅读推断与产品争议，用户已认可补建目标。范围选择读 [切片与场景范围](slices.md)，规则确认读 [业务设计](business-design.md)。未经确认的行为不能冻结为验收标准。

## 产出与确认

材料按需写入当前工作目录，例如 `prd.md`、`change-impact.md` 或 `business-expectations.md`，不要三份全建。更新 `state.md` 的来源、确认决定和待定问题。

需要人决定产品目标、范围和业务语义；已确认资料不重复请示。后续切片发现全局模型冲突时，提出修订并确认，更新唯一业务依据及受影响 Case，不能保留两套相互矛盾的真相。
