# 工作记录

## 目录与唯一来源

所有 Polaris 生成的流程文档、Case、反馈和执行证据放在目标项目的 `.hapilon/polaris/`，不是 Skill 安装目录。实现代码和可执行验收测试按目标项目约定放置，工作记录引用其路径；不要为归档复制业务代码。

```text
.hapilon/polaris/<工作名>/
├── state.md
├── scenarios.md
├── cases.md
├── acceptance-plan.md
├── evaluation.md
└── evidence/<执行批次>/
```

上图是示例，不是必建清单。工作目录内先平铺；证据数量多时单独分目录。不要按固定阶段预建文件夹。工作名用业务目标的简短名称；新工作重名时加数字后缀，接续工作沿用原目录。每项工作只有一个长期保留的目录，不另建集中 Case 库。

已有项目资料优先引用，不搬走、不复制成第二份真相。Case 草案与正式版本都留在本工作目录，用户确认后原地更新版本及确认记录，不搬家。跨工作复用时引用原文件路径、稳定 Case ID 和版本，不复制另一份正式 Case；修订提案获准后更新原文件并保留修订记录。

工作目录及正式 Case 不随工作结束而删除。Runner 按业务能力在项目测试目录中独立组织，不依赖工作目录中的临时执行产物。工作状态和报告记录 Case 的固定位置、版本及测试位置。

检查版本管理规则：正式 Case 与 Runner 应一起入库；日志、截图和本地状态默认保持本地。若 `.hapilon/` 被整体忽略，提出仅开放正式 Case 路径的改动，不直接放开全部产物。未获得项目允许前，明确记录“尚未纳入版本管理”，不要宣称基线已长期保存。证据不得包含密钥、令牌或未经脱敏的私人数据。

## state.md 的最小内容

- 目标与模式：本轮要完成什么，属于哪种入口。
- 范围与排除项：哪些业务能力可以动，哪些不动。
- 当前进度：当前流程阶段、所属父级业务切片、正在推进的技术批次、未闭环业务路径及下一步理由。技术批次通过与父级业务接受分开记录。
- 已确认决定：决定内容、所对应材料及版本、用户确认依据；没有确认就写待确认。
- 材料与证据：文件路径、Case ID、Runner 位置及实际运行入口，未建立的写未建立。
- 未解决事项：业务争议、风险、未验证边界与待处理反馈。

可增加任务需要的字段，不预造状态枚举、数据库或通用工作流引擎。批准记录必须能追到实际对话或其他明确依据；不得伪造消息编号、日期或批准者。

## 恢复工作

先读状态和关键材料，再核对当前代码与 Case 版本。状态只是接续索引，不是成功证据。

用户未指定工作时，只查看现有工作摘要。只有一个与当前目标明确匹配的未完成工作，可以说明后接续；存在多个合理候选时请用户选择，不按修改时间猜测。

分支、代码、Expected 或测试边界变化后，列出哪些旧结果不再适用。不能把旧 PASS 当新版本已验收。保留旧批次，不覆盖失败记录；根据变化确定需要重跑的 Case。

跨会话接续靠重新读取文件；如果文件缺失，说明缺失并恢复可证实的信息，不能凭记忆补造确认或执行结果。

## 长任务接续与汇总

沿用已有范围/切片索引作为当前业务状态的入口，不为每轮另造总体计划。阶段转换或批次完成时，同步该入口和state中的当前状态；详细历史结果留在各批报告，不让旧的“正在执行”与新的已接受结论并存。接续时发现冲突先核对真实产物，再修正入口，不按最新文件名猜进度。

连续进行多个模块、协议或探针批次而父级业务路径仍未闭环时，在继续派发前审查：新证据解决了什么、剩余阻塞是什么、下一个动作如何接回实际业务入口。确需继续拆分时说明原因；不能只凭局部测试数或提交数表示产品进度。项目要求同时迭代skill时，在这些节点记录流程问题及处置，沿项目约定归档修订，不为复盘另建大型流程系统。
