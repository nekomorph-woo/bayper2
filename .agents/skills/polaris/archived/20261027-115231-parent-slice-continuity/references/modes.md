# 任务入口

三种入口共用业务 Case、执行证据和人类决策，但起点与完成条件不同。本文件负责选择路线；各阶段的输入、产出和确认点在对应参考文件中。

从 [需求与 PRD](prd.md) 按当前模式开始，已有适用材料则复用。阶段可合并或省略不适用部分，但不能省略业务正确性确认或把未执行说成已通过。

## 从零开发

从想法、目标用户和产品资料开始，讨论形成 PRD 与全局业务模型骨架，再选一个可体验的垂直切片。切片按完整用户价值划分，不按前端、后端或数据库划分。

路径：Idea → PRD 与全局业务模型 → 切片规划 → 局部业务设计 → 已确认 Case → 技术与验收设计 → 实现与执行 → 人工体验决定 → 后续切片。

完成条件：当前范围的必需 Case 已实际通过，有证据；需要人工体验的部分完成后由用户决定是否接受。自动化通过与产品接受分别记录。

## 已有项目增量开发

先沿真实业务入口读现有代码、模型和测试；识别变化前基线，再设计增量。资料、代码或运行行为不一致时指出差异，不自动信任其中一方。

最小影响摘要包含：新增或改变的行为、复用的业务对象、必须保持的旧行为、需重跑的旧 Case，以及缺少回归保护的风险。

路径：新增需求与现有系统理解 → 增量需求与变更影响 → 本轮切片选择 → 业务设计 → 新 Case 与受影响旧 Case → 技术与验收设计 → 实现与回归 → 按影响范围体验。

完成条件：新增能力通过，受影响旧行为得到验证，未接受的退化不能被隐藏。明确的小 Bug 可直接采用“确认 Expected → 复现 → 修复 → 相关 Case 与回归”，无需重新规划产品。

## 存量代码补建验收

先选择有边界的业务能力，不全仓扫描生成几百条测试。阅读业务入口、核心路径、状态、副作用、既有测试和需求依据。

先整理场景清单，每项分别记录：实际行为、证据来源、业务依据、正确性状态。代码阅读只证明实现形状；未执行的行为标为阅读推断。

正确性状态分为：
- 已确认：有适用且已确认的业务规则，或用户本轮明确认可。
- 待确认：仅看到当前代码行为，尚无正确性依据。
- 已知缺陷：已确认违反业务预期；Case 按正确预期编写，不迎合现状。

路径：资料、代码与使用行为发现 → 场景清单 → 选择范围 → 还原业务规则与预期审核 → Case → 测试接入与验收计划 → Runner → 实际基线与遗留问题 → 按需要补充人工业务核查。

这里以业务预期摘要替代新建 PRD，不机械地从产品探索重来。

先请用户确认本轮范围和 Expected，再将草案变成正式 Case。待确认行为可用于明确标注的现状刻画测试，但不能当业务验收通过，也不能写入已确认基线。

原则上只实现 Runner 和获准的测试接入。若必须修改生产代码才能测试，说明最小改动及影响，等待授权；不顺手重构。

失败分流：测试代码、Fixture 或环境问题修复 Runner/环境；真实业务缺陷保留 FAIL 并登记；预期争议回到审核；无法判断记 INCONCLUSIVE。需要修业务时另开获准的修复工作。

完成条件：约定范围有已确认 Case、实际执行记录、清楚的覆盖和遗留问题。允许存在已知业务 FAIL，但必须与通过的回归基线区分；环境阻塞或未执行项不得冒充已完成验收。补建工作完成不等于产品验收通过。
