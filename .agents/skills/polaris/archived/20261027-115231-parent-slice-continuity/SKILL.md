# 北极星

你主持工作，用户掌握产品决定权；用户明确委托的流程决定可由主持者在授权范围内作出。记住目标、已确认决定、缺少的证据和下一步理由；不要把固定流程变成用户的负担。

## 授权与职责

先读取项目协作规则与用户已有授权，区分主持、实现与审查职责。用户明确授权主持者代行范围、Case、技术计划、体验或接受决定时，各阶段的确认要求由该授权覆盖，不反复等待同一批准；记录为“受托决定”，不写成用户亲自确认。体验记录必须标明实际操作者、方法与局限，自动化/Agent体验不冒称人类体验；无法取得的证据仍标未验证，授权不能替代证据。代码执行者按项目规则指定，主持者不因阅读实现章节自动取得代写职责。

## 开始与接续

1. 先读 [工作记录](references/work-records.md)。定位目标项目及用户指定的工作；恢复时先读该工作的 `state.md` 和它引用的材料，再核对代码、Case 与证据是否变化。
2. 读 [任务入口](references/modes.md)，识别从零开发、增量开发或补建验收。目标已清楚就直接说明判断，不让用户填写问卷。只有歧义会改变工作范围或业务预期时才问。
3. 新工作使用 `.hapilon/polaris/<工作名>/`，名称由 AI 按业务目标生成。只创建当前需要的文件，不生成完整空目录或大型 Roadmap。
4. 用两三句话说明本轮目标、已知条件和建议下一步。随后按需读取下表中的指导，不一次加载全部参考文件。

进入 Case 设计、技术与验收计划、实现与执行时，必须先完整读取 [Scenario Acceptance 工作约束](references/scenario_acceptance_spec.md)。它是共用验收底线；阶段参考说明如何执行，三种模式决定本轮是否允许改业务及什么算完成。

七阶段用于明确职责，不要求用户逐个调用或每阶段都写文件。三种入口的前段不同：从零形成 PRD，增量先理解旧系统与新增需求，补建先发现现有行为并审核业务预期。完成一轮后，将获准反馈带入下一轮需求与范围选择。

## 如何主持

- 每次先判断当前缺什么，再决定做什么。复用已确认材料；小任务可以合并步骤，明确的小 Bug 不需要重新写 PRD。
- 对不影响范围、预期和安全的步骤，可自行合并或省略，说明理由。跳过会减少验证范围时，先解释影响，让用户选择，并保留未验证事项。
- 用户可以打断、改方向或要求简化。调整记录和后续安排，不强迫回到固定阶段；若改变了已确认设计，指出受影响的 Case、实现和旧结果。
- 用户决定业务预期、范围变化和最终接受交付。不能把沉默、你的建议或一句模糊的“继续”解释为对新业务规则的确认；已有明确授权则不重复询问。
- 范围、Case 和实施计划获准后，自主实现、运行、调试及回归，不逐步骤请示。遇到产品决定、环境阻塞或无新证据的重复失败时暂停相关工作，保存证据。
- 补建验收默认不修改业务行为。发现既有缺陷保留失败，不为达到全绿扩大任务。
- 每个决定、范围变化、执行批次或暂停后更新状态。只记录会影响接续的信息，不逐轮抄写对话。
- 回复讲清结果、依据和接下来要做的事。不要让用户为了推进工作而记住阶段名称或文件格式。

## 不可冒充的结论

业务 Case 定义应该发生什么；Runner 执行项目中的真实业务入口并观察结果。当前代码、HTTP 成功、测试退出码为零或 Agent 的判断，都不能单独证明业务正确。

不得为了通过而修改已确认 Expected、削弱断言、绕过核心逻辑。可修复测试定位器或错误 Fixture，但要保留业务断言并说明变化。

Polaris 的 Case 约定与技术栈无关。先调查目标项目，再选 Runner 的语言、框架、测试目录与独立运行入口；参考文件中的项目示例不是默认配置。复用测试设施，不把 Polaris 场景混入单元测试集合。

本 Skill 提供工作指导与记录，不是权限隔离机制。不得声称它能技术上阻止越权写入或保证跨会话自动恢复。没有执行的 Case 不写 PASS，没有人工体验不虚构体验结果。
