# 验收 Case 设计

## 输入

先完整读取 [Scenario Acceptance 工作约束](scenario_acceptance_spec.md)，本文件只补充设计流程与关联方式，不替代该约束。

读取已确认需求、当前范围和业务设计。新增开发设计新 Case；增量开发同时选择受影响旧 Case；补建验收依据已审核的业务预期编写，不能把现状刻画测试直接当正确答案。

## 设计

先给简洁的场景覆盖矩阵，再展开本轮必要的 Case。覆盖核心正常路径、重要边界、异常、状态转换与不变量，按业务风险选择，不做无意义的组合穷举。

每个场景从业务入口到最终业务结果，不退化为单元测试、单步 Prompt 测试或内部方法测试。每条 Case 包含：
- 稳定 ID、业务名称、需求或规则来源。
- Given：业务初始状态与必要条件。
- When：完整业务操作。
- Expected：可观察的结果、状态、副作用，以及禁止发生的副作用。
- Oracle：如何独立判定正确；区分确定性断言、模型语义评估与人工判断。
- Execution Boundary：要求验证的范围、真实依赖与允许的 Mock 边界；无法确定的部分标待确认，技术阶段再细化，不悄悄降低业务目标。
- Priority：风险优先级及是否为本轮必需场景。
- 确认状态和版本；获准后补充确认依据。

Case ID 在项目中唯一、跨工作稳定，不因文件移动或排序改变。可采用 `POL-<业务能力>-001`，优先遵循已有命名约定；废弃 ID 不复用，业务预期变化保留修订记录。

设计阶段只有 Expected，没有预填 Result。Expected 不能复制执行结果，Oracle 不能调用被测实现计算同一个“正确答案”。涉及模型语义评估时明确标准、评估者与不确定性；一句“正确”不能替代证据。

识别无法客观验收的需求、规则遗漏和矛盾。存在产品歧义时提问，不自行改 Expected，也不为了便于自动化而削弱它。回到 [业务设计](business-design.md) 澄清后继续。

## 产出与确认

产出供用户审核的 Acceptance Cases；草案保留在当前工作目录。完成条件：本轮场景覆盖和 Expected 获准，未解决项与排除范围明确；已有适用确认直接复用。

本阶段不编写测试代码、Runner 或详细技术方案。确认后按 [工作记录](work-records.md) 在 `.hapilon/polaris/<工作名>/cases.md` 原地登记正式版本，不搬到集中 Case 库，再读 [技术与自动化验收计划](acceptance-plan.md)。

## 与 Runner 的关联约定

Case 定义业务承诺，与语言、框架、命令和测试文件后缀无关。Runner 由目标项目的技术栈实现。

实施时在正式 Case 或相邻索引中补齐 Case ID → 测试文件及测试名称 → 实际运行入口。路径从项目根目录定位，不依赖机器绝对路径。测试名称或框架元数据携带同一 ID，执行报告按 ID 汇总。

一个 Case 可对应多个测试或人工核查项，必须列出全部必需项及聚合规则；全部通过才记 PASS。子项标识明确，不能互相覆盖结果。未覆盖、跳过、只执行部分断言均显式记录。

正式 Case 保持唯一版本；Runner 按业务能力独立于单元测试组织，不依赖工作目录中的临时执行产物。目录、测试集合或标签及独立运行入口在技术阶段按项目确定，验证单元测试入口不会混入 Polaris 场景。
