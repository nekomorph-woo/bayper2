# 技术设计与自动化验收计划

## 输入

先完整读取 [Scenario Acceptance 工作约束](scenario_acceptance_spec.md)，再读取已确认需求、业务设计和 Acceptance Cases。计划要同时回答如何实现、如何证明业务预期成立。

## 一次设计，两个部分

两部分协同设计、分别输出、联合审核，可以保存在同一个 `acceptance-plan.md` 中，但不能把技术设计与验收计划混成一张任务清单。

### Part A：Technical Design

调查项目语言、构建方式、现有模块、数据与接口、错误处理和技术约束，优先复用已有能力。

说明本轮必要的模块、业务对象数据结构、接口契约、状态处理与核心执行流程，明确外部依赖、异常处理和关键取舍。每条已确认业务规则与 Case 均应有实现路径；不为未来切片建设通用框架。

从零开发设计当前切片；增量开发说明复用和改动影响；补建验收通常只需测试接入设计，不重新设计业务架构。必须改生产代码才能测试时，解释最小改动和影响，另行取得授权。

### Part B：Automated Acceptance Plan

每条 Case 分别说明：
- Setup：可重复的初始环境、数据与 Fixture，以及清理方式。
- Driver：实际执行的业务入口。
- Boundary：真实运行的依赖与 Mock 范围，包括真实模型调用和确定性逻辑的边界。
- Observation：实际结果、业务状态与必要副作用如何观察。
- Oracle：独立的业务断言、语义评估或人工核查方式。
- Evidence：保留哪些执行记录，使结论可复查。

Driver 经过真实核心业务逻辑，Mock 只放在获准的依赖边界。Fake 存储只能证明模拟状态，不能证明真实介质持久化。完整 E2E 环境不可用时，提出可执行的场景级方案并明确未验证的生产流程，不自行缩小已确认的验收目标。

## Runner 接入

调查并复用项目现有测试框架，不另造通用 Runner 平台。为 Polaris 验收选择独立目录、测试集合或标签，提供专用运行入口。核查默认测试发现规则，确保开发时单元测试命令不混入这些场景；总回归可以显式组合两者。

沿用 [Case 关联约定](cases.md) 建立 ID 与测试映射。按项目确定语言、路径和命令，不把某个技术栈当默认前提。例如项目可复用 JUnit、pytest、Vitest 或 Playwright，但这些只是示例，不是安装要求。

明确真实服务、凭据来源、费用和破坏性操作，按项目权限取得授权。优先隔离环境和可重置数据，不操作生产数据，不将凭据写入产物。

## 产出、联合检查与确认

建立 Case → 实现模块 → 验收方式映射，检查每个 Case 是否可执行、结果可观察、Oracle 独立、Mock 未绕过核心逻辑，以及方案是否过度设计。再对照本轮业务目标核查验收计划是否真正覆盖目标，不能只做到已有 Case 各有一个测试。列出只能人工验证、缺少观察手段或存在技术风险的部分。

已确认模型或 Expected 存在问题时提出修改建议，不自行改动。范围变化回到业务审核；不能为降低接入难度而改变正确性标准。

完成条件：技术设计和自动化验收计划获准，风险、必要授权与未验证边界明确。本阶段不编写业务代码或 Runner。已有实施授权覆盖当前计划时可直接复用，不重复请示；否则等待审核。

获准后读取 [实现、执行与报告](execution.md)，自主推进实现与验证。
