# Bayper PRD

状态：讨论草案，持续原地更新；尚未完成范围确认或进入实现。更新日期：2026-10-25。

## 产品定位与起因

Bayper 是可独立启动和持续运行的桌宠应用，首先提供有生命感、有性格、能互动的桌面陪伴。外部应用通过“连接器”与 Bayper 关联；Herdr 是当前明确的连接对象，通过 Herdr 插件接入 Bayper 的对应连接器。连接 Herdr 后，Agent 状态变化通知是核心必需能力，不能被宠物的自主性压制。

用户的初始动机：终端中的 AI Coding 过程随着时间变长，容易变得百无聊赖。Bayper 希望让这段工作与等待多一点趣味和陪伴，值得长期留在桌面上。状态感知服务于这个定位，不能单凭状态显示正确便认定核心价值成立。

当前首先面向用户本人，优先 macOS 自用；画风采用第二轮猫咪女仆16宫格的10号：精细二次元像素、可见细密纹理与紧凑头身，后续素材保持该画风和比例，不需要3D。角色采用用户所说的“娘化”方向，即具有女性角色特征的拟人形象，而非纯动物造型；兽耳、尾巴与人形服饰结合是风格比较的示例，不代表所有个体必须是猫。暂无面向公众分发的要求。

## 核心体验方向

1. **日常陪伴**：用户工作时，宠物有自己的活动，主要用动作、表情和偶尔的短句表达，让用户感觉它持续存在；自主活动不能以干扰工作为代价。
2. **主动的小惊喜**：等待 Agent 时，宠物偶尔发起互动；如何辨认等待、如何控制频率、用户不回应时如何处理，仍需讨论。
3. **回应用户**：用户主动关注它时，宠物给予有辨识度的回应；用户可主动发起文字聊天。回应能够延续以往互动形成的熟悉感；具体入口、动作、聊天呈现及变化机制尚未决定。
4. **独立运行与连接**：Bayper 可先独立打开；Herdr 通过插件与连接器建立关联后，Bayper 提示“Herdr 已上线～”。Herdr server stop 后提示下线，桌宠继续运行与陪伴。
5. **必需的工作状态通知**：接入 Herdr 后，Agent 状态变化必须通知用户。宠物可以以自己的性格表达，但不能因情绪、自主活动或不愿配合而漏掉、拒绝或无限拖延通知。通知形式仍待细化；聚合、展示和最大等待先采用下方待验证的默认方案，不代表已经过体验验收。

上述是用户需求的整理，不是已冻结的功能列表、动作清单或正式验收 Case。

## 独立桌宠与连接器

### 运行关系

Bayper 有自己的启动、运行和退出生命周期，不依赖 Herdr 已安装或正在运行。没有 Herdr 连接时，仍可进行日常活动、直接互动、文字聊天与已有记忆支持的陪伴；首次使用的强制模型配置要求保持不变，模型服务异常时的具体规则仍待细化。

“连接器”是 Bayper 关联外部应用的边界。当前明确 Herdr 插件与 Bayper 对应连接器关联，让外部应用的上线/下线与工作事件进入 Bayper 的表达。Herdr 插件的启停不再等同于 Bayper 本体的创建与销毁。

### 已明确的相处场景

| 场景 | 期望 |
| --- | --- |
| 独立打开 Bayper，Herdr 未运行 | 完成首次必要配置后，桌宠可以正常陪伴，等待未来建立连接 |
| Bayper 已运行，Herdr 启动并建立关联 | Bayper 向用户提示“Herdr 已上线～”，开始接收其工作状态变化 |
| Herdr 已运行，随后打开 Bayper | 在对应插件可用的前提下自动发现并连接；首次建立该关联后提示上线，不要求用户重启 Herdr |
| 已连接的来源暂时断联后恢复 | 自动重连；同一来源恢复不反复播报“已上线”，具体恢复提示按下方规则 |
| Herdr 已连接，Agent 状态发生变化 | 必须通知用户，表达可带角色性格，通知不能被自主性取消 |
| Herdr server stop | Bayper 向用户提示 Herdr 下线，结束该连接的在线状态，Bayper 自身继续运行 |
| 未来接入其他应用 | 沿连接器边界扩展，不将所有外部来源固定成 Herdr 概念 |

这里的上线提示由 Bayper 向用户表达，不是将该提示发送给 Herdr。上线代表对应关联已经可用；下线与 Agent 的任务完成是不同事件，不互相替代。

### 连接器、实例与归属（当前已认可）

Bayper 核心只需要理解连接器类型、具体连接器实例、来源身份及其事件，不要求所有连接器都具有 Herdr 的 server、session、pane 结构。Herdr 插件是对应的适配入口；Herdr 侧的具体层次由 Herdr 连接器解释，再向 Bayper 提供可区分的来源和 Agent。

用户本轮认可当前按以下关系组织：

| 对象 | 归属与职责 |
| --- | --- |
| Herdr 连接器类型 | 说明怎样与 Herdr 插件关联，以及怎样解释 Herdr 的连接与工作事件 |
| Herdr 连接器实例 | 当前一个 Herdr server 对应一个实例；多个 server 表现为多个 Herdr 来源实例，各自上线/下线 |
| 会话与来源内上下文 | 由所属实例维护，作为 Agent 的归属和显示线索；不因为增加会话就要求 Bayper 核心创建新连接器类型 |
| Agent | 在来源实例内独立识别和维护状态，可附带所属会话/工作区/终端的可读信息；不与其他 Agent 合成一个总状态 |

用户本轮已接受“一个 server 一个实例、会话在实例内、Agent 独立”的当前归属方案，后续修订需同步影响记录。身份不能仅使用显示名称或局部 pane ID：应能区分来源实例，以及同一位置中新启动的 Agent；具体稳定标识与运行代次留待技术设计。一个实例下线不代表其他实例下线。

用户已明确最多同时存在 3 只 Bayper；其与连接器/Agent 的关系按下方“宠物数量、陪伴与接续”建议细化，不由来源数量自动决定。多个实例需要可辨认的名称或线索，使用户能知道哪个 Herdr 来源上线、哪个 Agent 发生变化。

### 自动发现、重连与上线提示（Codex 建议规则）

用户已明确双向启动顺序都应自动关联、断连自动重连、避免重复上线播报。建议将连接事实与提示分开处理：

| 情境 | 连接行为 | 提示行为 |
| --- | --- | --- |
| 本次 Bayper 运行中首次发现并成功连接某来源实例 | 开始接收事件并取得当前状态 | 对该实例提示一次上线；重复发现、登记、握手或心跳不重复播报 |
| 同一来源运行期间短暂断联 | 自动尝试重连，暂时保留来源身份；其 Agent 状态标为暂不可确认，而非任务完成 | 短暂抖动不反复触发上下线动画；持续断联满默认 3 秒后提示一次“暂时断联，正在重连” |
| 同一来源恢复 | 恢复连接并对账当前各 Agent 状态 | 不重新播报“新上线”；若此前已提示断联，可提示一次“连接恢复” |
| 确认对应 Herdr server stop | 结束该来源本次在线生命周期，Bayper 继续运行 | 提示该实例下线一次；重复断开信号不重复通知 |
| server 真正重启并重新可用 | 识别为新的来源运行周期，并重新关联 | 允许新的上线提示一次，不把真正重启当作重复握手过滤 |

“第一次连接”对已经运行的 Herdr 也适用；不能要求只有插件 startup 与 Bayper 同时运行才可接入。Bayper 打开时的初始状态快照用于建立现状，不冒充刚发生的 Agent 状态变化。

自动重连持续到来源恢复，或用户明确断开/停用该连接；不以后台重连绕过用户主动停用。重试节奏留待技术设计；暂时断联提示的默认观察期为 3 秒，详见通知方案。暂时联系不上不能直接证明 server 已 stop；若实现无法明确区分，需保持断联/未知语义并如实说明，不虚构停止事实。

### 独立 Agent 状态与通知节奏（Codex 建议规则）

每个 Agent 的状态与变化独立记录。A 在工作、B 需要用户介入、C 已完成时，三者应同时保持各自状态；不能用“Herdr 整体工作中”覆盖 B 或 C，也不能只关注当前聚焦的一个 Agent。

建议把状态更新、通知内容与宠物表演分开：

1. **状态及时更新**：已观察到的真实变化立即更新对应 Agent 的状态，不等待动画结束或播报轮到它。同状态的重复快照/重放可以去重；“工作→待介入→工作”是真实的多次变化，不能因首尾相同就抹掉中间事件。
2. **短时间成组表达**：同时或短时间内出现多条变化，可以用一条清楚的合并播报承载多个 Agent 的变化，并保留各自可回看的通知明细。例如“A 已完成；B 需要你确认”，这是合并呈现，不是合并 Agent 状态。同一 Agent 短时间多次变化也应表达过程，例如“B 曾等待确认，现已继续工作”，不能只留下最终工作状态而隐藏中间变化。
3. **动作保持可读节奏**：同一时刻不因多个 Agent 争抢而快速切动作；按下方默认最短展示时间与可中断规则执行，后续以体验调整数值。已更新的状态明细与正在表达的历史事件应可区分，不能把过时的“开始工作”当作当前仍在工作。
4. **重要事件优先且保留其他变化**：建议需要用户介入的事件优先、完成事件随后、普通进展按节奏表达。被打断或尚未表达的通知仍须进入后续合并播报/明细，不能因冷却或性格而丢失；避免普通变化被持续高优先级事件无限拖延。
5. **避免积压后的连续爆发**：重连或短时大量变化后，先对账现状，再清楚汇总已有记录；不逐条重放过时动画制造通知轰炸。每个受影响 Agent 的变化仍可区分，不能仅以“有多个更新”替代必要内容。
6. **去重针对事件身份**：同一真实事件只通知一次；同一 Agent 后来再次进入相同状态属于新的变化，仍需通知。Agent、连接实例的身份与运行周期参与区分，具体幂等方式留待实现设计。

以上呈现策略与下方数值由 Codex 提出，作为待验证的默认方案；用户已接受归属方案，并要求先保留通知默认值、后续体验调整。通知呈现按本轮用户提出的多气泡队列调整；具体样式与声音方案未确定。必需通知意味着变化得到明确表达，不能以后台悄悄写入一条记录替代用户可感知的通知。

断连造成的未观察历史，沿用前期研究边界：恢复快照只恢复当前状态，不能虚构缺失事件。需要提示恢复期间的观测缺口；已知事件去重、当前状态对账与历史是否完整分别判断。

### 播报与通知的默认数值（Codex 方案，待验证）

这些数值用于后续原型与验收场景的起点，当前不实现调度器，也不宣称已验证无漏通知或无闪动。

#### 优先级、聚合与最大等待

| 优先级 | 适用事件 | 最长聚合时间窗 | 首次可见的最大等待目标 |
| --- | --- | --- | --- |
| P0：需要用户处理 | 来源明确表达的待确认、需输入或其他需要用户介入的变化 | 0.5 秒 | 1 秒 |
| P1：重要结果/连接异常 | 本次工作结束、结果待查看；确认来源下线、持续断联提示 | 1 秒 | 4 秒 |
| P2：普通进展/连接提示 | 开始或继续工作、普通空闲等其他真实状态变化；首次上线、同周期连接恢复 | 2 秒 | 8 秒 |

优先级依据来源已经确认的含义，不凭模型猜测任务成功或错误；Herdr 的 done 不自动等于业务成果成功，状态映射仍需后续明确。没有明确语义的其他真实变化先按 P2 呈现，不静默过滤。

- **计时起点**：从 Bayper 接收该真实变化并识别其身份时计时；不含外部传输延迟。持续断联提示先观察 3 秒，仍未恢复才产生一次 P1 通知；确认 server stop 无须额外等待这 3 秒。
- **固定收集窗**：窗口从这一批最早未表达事件开始，不因后续事件不断到达而延后；可提前结束窗口，将低优先级变化顺带纳入高优先级批次。每个事件仍保留自身的目标截止点，不能借追加事件或合并批次重置计时；多气泡排队导致的超时按下文容量冲突处理，不伪装为准时。
- **最大等待的含义**：变化内容进入用户可见的通知表达，包括具名的分组子项；不要求每个事件各占一次独立气泡、独立台词或完整动画。仅在后台记入历史不算达标。默认不自动发声或生成系统弹窗；这两种渠道的启用方式另议。
- **调度与公平性**：批次先按最早截止时间处理；截止时间相同时 P0→P1→P2，同级按接收顺序。默认时效仍作为目标；当前新增同屏气泡容量和排队约束后，极端突发下能否同时满足时效与最短展示，需要后续验证，不能通过静默丢弃或无限抢位解决。
- **模型不阻塞必需通知**：若个性化措辞未及时可用，先用已知事实形成简短表达，满足截止时间；后续不为换一句模型台词重复通知同一事件。

#### 最短展示与防闪动

| 呈现对象 | 默认值 | 例外与含义 |
| --- | --- | --- |
| 普通通知内容 | 至少可读 4 秒 | 不因低优先级事件到达立即换掉；用户主动关闭除外 |
| P0 内容 | 至少可读 6 秒 | 仍需介入时保留稳定的待处理标记，不每隔 6 秒重新弹出 |
| 宠物一次状态表达动作 | 默认至少保持 1.5 秒 | P0 可在合适过渡点中断低优先级动作；必要文字通知不等待动作结束 |
| 同屏气泡数量 | Codex 建议默认 N=3 | 是整个桌面的通知容量，与宠物最多3只不是绑定关系；额外气泡进入队列，待空位出现 |

气泡采用并行展示加排队：有空位时可同时显示多个独立气泡，最多 N 个；没有空位的气泡在队列等待，每个气泡在实际显示后独立计算普通4秒/P0 6秒的可读时间，之后逐渐消散，不能把排队时间算作展示时间。同批可按 Agent 组织多个变化的具名内容，各条原始变化仍保留明细。新气泡不覆盖或挤走正在显示的气泡，不因后续入队重置旧气泡计时；具体摆放与消散动画留待原型。

若某条待介入事件在窗口结束前已恢复，仍表达“曾需要确认，现已继续工作”，按原 P0 截止时间呈现；当前待处理标记同时清除，不以过时指令继续催促用户。通知记录保留真实顺序。

本轮呈现变更替换了“新独立气泡最快4秒一次、紧急内容争用同一稳定区域”的前版建议；聚合窗、内容最短展示、动作节奏和时效目标先保留。必须如实记录容量冲突：例如3个P0气泡都需展示6秒时，第4个P0若排队，就无法保证1秒内完整气泡可见。当前不宣称这些约束已完全兼容；是否提供独立的即时待处理提示、允许紧急临时额外容量或调整时效定义，留待后续专门讨论，不能擅自缩短展示、挤走旧气泡或把入队冒充已经通知。

#### 批量、积压与重复的处理

- 每个真实变化保留连接器实例、Agent 身份、发生/接收时间（来源未提供时不补造）及表达状态；去重仅合并同一事件的重复传送，不合并两个不同 Agent，也不删除同一 Agent 的往返变化。
- 同批表达可按 Agent 分组，例如“来源甲：A 已完成；B 曾等待确认、现已恢复”。多 Agent 大批到达时，每个受影响 Agent 都有具名子项及变化详情；可以成组阅读，不逐个播放独立动画或语音。折叠摘要必须能显露受影响来源/Agent 和当前含义，不能只剩一个笼统计数。
- 达到 P1/P2 截止时间但 P0 仍持续到达时，优先安排已到期内容的队列位置，空位释放后尽快呈现；同屏容量导致的时效冲突需显式处理，动作可以代表当前高优先级情境，具名内容负责完整传达各 Agent 变化，不生成“所有 Agent 的综合状态”。
- 恢复后新收到的补发历史按此次接收时间进入一次汇总，标注历史与当前状态：已结束的历史待介入/结果按 P1，其他历史进展按 P2，分别遵守 4/8 秒截止时间。断连前已接收但未表达的事件不能借重连重置其原截止时间；若某个 Agent **当前**仍需介入，对该现状用 P0，以 1 秒内可见为目标；同屏容量不足时按已记录的冲突处理，不宣称硬保证。无法观察到的缺失历史单独说明，不补造变化或成功事件。
- 已经通知过的 P0 持续不变时，不定时重复弹出；保留待处理标记。用户处理后再次进入待介入，是新事件，重新通知。短断联自动恢复且未达到 3 秒观察期时，不新增上下线播报。

#### 用于审阅默认方案的时间示例（非执行证据）

| 构造场景 | 默认方案的期望 |
| --- | --- |
| t=0 A 开始工作；t=0.4 B 需要确认；t=0.7 C 完成 | B 最迟 t=1.4 可见；可以在同批提前带上 A/C，三者状态分别保留，不连闪三段动作 |
| t=0 正在显示1个普通气泡；t=0.2 D 需要输入 | 尚有空位，D 可用独立气泡尽快显示，以 t=1.2 为目标；普通气泡按自身时间消散 |
| 同屏气泡已满且 P0 持续到达 | 全部事件保留，按时效目标与优先级排队；8秒普通事件目标是否可满足需与容量策略一起验证，当前不保证极端突发仍全部准时 |
| A 在 0.3 秒内工作→需确认→继续工作 | 每次变化保留；一组表达该过程与当前状态，不误报 A 仍等确认，也不抹掉中间状态 |
| 同一连接断开 1 秒后恢复 | 后台自动重连，不播报下线/新上线；若持续超过 3 秒则按断联规则提示一次 |

以上为建议的体验预算，不是实时系统保证。系统休眠、Bayper 未运行及外部事件缺失不计为正常接收后的调度场景，须在恢复后解释现状与缺口，不能声称用户已收到所有离线变化。

### 当前边界与后续讨论

- 当前只明确 Herdr 适配，其他应用沿连接器边界扩展，不建设插件市场或通用扩展 SDK。
- 自动关联与重连是产品要求；发现与通信协议、来源标识、插件在 Bayper 未启动时怎样保持可发现性，留待技术设计核实，不在 PRD 中冻结具体 API 或进程组织。
- 连接器接收工作事件与 Coding Agent 会话目录访问是不同能力。建立 Herdr 连接不代表允许分析外部会话，默认关闭及明确目录授权的要求保持不变。
- 前期生命周期探针中随 Herdr stop 结束测试 GUI 的行为只说明原实验切片，不作为独立 Bayper 的产品目标；窗口、事件、安装与进程实验可按边界引用，不把旧实验通过当作新生命周期与通知节奏已验证。

## 宠物数量、陪伴与接续

### 已明确的世界观与上限

Bayper 应用与其中的 Bayper 个体是不同对象。用户与所有个体都是流浪者，共同建立友情与亲情；陪伴包括个体与用户的关系，也包括个体彼此的关系。不存在婚恋、繁殖、后代出生或以血缘解释继任的系统。

最多同时存在3只 Bayper。用户以“旅行青蛙”作探索与离开的体验类比，本 PRD 仅记录用户明确描述的临时出门、独自闯荡和新流浪宠物入住，不据此认定该游戏具有相同机制。

### 数量与名额（用户已确认）

- 默认从1只开始，随相处遇到新的流浪宠物，逐渐形成最多3只的陪伴关系；不要求开局凑满3只。
- 3个上限按“在住名额”计算：临时外出的个体保留名额和关系，保证返回时不会变成第4只；同屏在场数量因此可能少于3。
- 永久离开后释放名额，新继任者以新的流浪宠物身份入住；旧个体可保留离开记录与可传承记忆，不继续作为在住个体活动。
- 有空余名额时可遇到新的流浪宠物，用户明确接纳后才入住，用户也可以拒绝；不自动替换现有个体。
- 满3个在住名额时，默认探索不出现发现新流浪宠物的行为，不预先生成第4只到访或等待入住的个体；临时出门不改变满员判断。
- 满员仍可发现其他流浪宠物的居所信息，向用户播报并偶尔提供简单选择题，了解用户的角色偏好。取消运行时生成图片后，建议这些倾向用于版本内已有角色的相遇选择；具体关联规则待讨论。线索不占名额、不承诺入住，也不导致现有个体离开；之后有空位时，新入住仍需用户确认。

### 宠物与连接器、Agent 的关系（Codex 建议）

| 对象 | 建议关系 |
| --- | --- |
| Bayper 个体 | 独立身份、性格底色、相处习惯、情绪和个人经历；不因连接器断开或 Agent 退出而消失 |
| 连接器及实例 | 属于 Bayper 应用，承载真实来源身份和事件；新增连接不自动生成宠物 |
| Agent | 仍属于来源实例并保持独立状态；不与某只宠物的人格、生命或记忆一一绑定 |
| 通知表达者 | 默认由一只当前在场的 Bayper 承接工作通知，用户可指定偏好；它只代为表达，不“成为”对应 Agent |
| 同伴互动 | 在场个体可彼此陪伴并形成关系与经历；不要求所有个体随每个 Agent 变化一起切动作或重复播报 |

建议每个通知气泡同时能区分**表达者**与**事件来源**：例如“由小灰转告｜Herdr·实例甲｜Agent A：需要确认”。多个 Agent 可以由同一只 Bayper 转告，同一事件仅生成一次通知；气泡独立排队与消散，不要求每只宠物固定占一个通知槽位。

表达者临时出门、永久离开或暂不可承接时，由其他在场个体接续，未表达事件保持原来源和队列身份，不因换表达者重复上线或丢通知。若全部个体都临时外出，Bayper 应用继续接收连接事件并直接提供具名来源通知；不为通知强行创造第4只宠物，也不把某只宠物虚称为仍在场。具体通知入口与外出者是否远程表达，待体验设计。

### 临时出门、永久离开与新入住

用户明确两种离开：临时出门后可返回，永久离开则去独自闯荡，之后的继任是新流浪宠物入住。Codex 建议：

- 临时出门保留身份、已形成的关系和个人记忆；返回延续相处经历，不重新抽取性格。
- 永久离开结束在住身份，不等于删除历史与所有记忆。建议由用户明确确认后生效，个体可以表达出发意愿；是否允许自主永久离开、是否保留联系，仍待讨论。
- 新个体保留自己的初始性格和身份，逐渐认识用户与其他在住个体；不当作旧个体重生、复制人格或其后代。
- 个体出入不改变应用生命周期、连接器归属或 Agent 状态；永久离开不能连带丢失尚未表达的必需通知。

### 记忆传承

用户明确每个 Bayper 的记忆可以传承给新 Bayper，用于新的流浪宠物接续入住。传承不是出生机制，也不自动表示所有记忆共享或所有个体人格相同。

当前组合方案采用轻量“行囊”表达传承：优先包含仍有效的重要偏好、少量共同故事与必要关系背景，保留整理者与讲述来源。Codex 本轮细化建议接收前由用户预览、选择部分或不传，也可入住后再交接；这些细节尚未逐项体验确认，详见下方现行组合方案。

传承的内容记录原来源与传承关系，新个体可表达“前辈告诉过我……”，不把获知的历史说成自己当时亲历。原个体的临时情绪不直接变成继任者的性格底色；用户的新纠正仍须对现行有效理解生效。传承派生信息如何处理纠正/删除与范围撤销，需与记忆规则一起研究，不在本轮冻结存储结构。

### 探索的实际含义

按用户补充，探索主要是以角色活动承载真实的了解与记忆工作，包括：

- 在用户已授权且当前启用的数据源中了解新的会话内容，构筑可修正的初步了解。
- 整理已有记忆，提炼重要偏好与共同经历，处理修正、细节淡忘与传承准备。
- 将旧个体留下的记忆交接给新入住个体，形成具有来源的传承经历。
- 有空余名额时发现新的流浪宠物，为后续邀请与入住提供相遇契机；满员时默认只带回居所信息，不发现新的个体。出现时机、线索与未来候选怎样关联仍待细化，不宣称能从任意文件中直接发现真实宠物。

外部会话分析默认关闭、必须明确请求对应目录访问的规则保持不变。出门或探索本身不产生新的读取权限；没有授权外部源时，可以围绕已有 Bayper 互动与记忆活动，也可以休息。探索不要求擅自访问整个磁盘、联网漫游或控制 Coding Agent。

角色叙事与实际工作应对应：没有执行的来源分析或记忆整理，不显示为“已完成”。临时外出可承载一段活动，但活动本身是否必须离开屏幕、允许多久、怎样反馈成果、后台失败后怎样回来，以及永久离开与传承的先后顺序，留待讨论。当前不进入旅行玩法、地图或实现设计。

### 造型元数据库与角色制作来源

候选仍不等于现成图片部件。当前正式可发布素材与完整动画均为0，描述配方不能直接放入可相遇集合。

### 发现、入住与传承的当前组合

- **发现**：以轻量偶遇为基础，同一居所线索连续积累、重复信息合并；有空位且存在已发布素材后才形成具体相遇。同伴可以引荐，也保留自然偶遇；满员默认只有居所线索，不预创建屏外新身份。选择题可跳过，答案作为暂定倾向，不自动固化偏好。
- **入住**：Codex细化默认一次只保持一个待处理邀请，轻量介绍后由用户接纳、暂缓或拒绝；沉默不当同意。接纳时复核名额，满员不自动挤走旧个体，拒绝不惩罚也不立即换人重复询问；已有候选不因重启或更新随机换身份。
- **记忆传承**：采用小行囊而非全量人格复制，记录谁留下、谁转述、谁接收；建议由用户预览选取，可拒绝、稍后处理或入住后接收。交接前与接收时核对现行有效记忆，不因传承复活已纠正/删除内容，也不传递外部目录读取权限。新个体保留自己的底色，通过相处建立新关系。
- **离开与必需能力**：临时出门占名额、永久离开释放名额保持；永久离开由用户明确确认是当前建议默认。发现、引荐、离开和传承分别发生，不互作奖励或强制门槛；无宠物在场时应用仍履行Agent通知。

用户确认的是组合方向；上述本轮细化来自Codex整理，尚无实现或产品体验。频率、冷却、拒绝后重逢、永久离开后联系、传承摘要入口与删除传播范围继续讨论，不在本轮冻结数据库实现。

## 性格与记忆

已明确：

- 初见时已有自己的性格底色，可以包含随机与未知感；用户通过相处慢慢认识它，性格不完全由用户预先设定。
- 此后通过相处逐渐成长。日常表现与主动聊天属于同一只宠物，跨次相处应延续之前的熟悉感。
- 记忆重点包含用户偏好与共同经历，并自然影响之后的动作、表达、主动邀请及聊天回应。记忆的保留粒度与实现方式尚未确定。
- 会话分析所得先作为初步了解，允许通过后续相处逐渐修正；不因单次任务就固定用户偏好。
- 琐碎细节可以自然淡忘，重要偏好与共同经历希望长期保留；用户明确纠正时，应及时更新记忆及后续表现。
- Bayper 维护自己的记忆；用户直接沟通、双方互动与经授权的外部会话分析都可提供来源，外部会话目录不承担 Bayper 的记忆存储职责。

待讨论：

- 在已认可的三层性格框架中，哪些具体特征相对稳定，习惯成长的幅度与速度，以及情绪如何变化和恢复。
- 怎样判断重要偏好与共同经历、哪些琐碎细节可以淡忘；如何在后续相处中自然体现记忆，以及何时需要提及过去。
- 用户明确纠正须及时生效已确定；查看、删除或重置记忆的入口与规则，以及冲突、误解和遗忘时的具体表现仍待讨论。
- 离开、重启及更换模型后的具体记忆与性格连续性规则。

### 性格成长的三个层次

用户已认可：

- **性格底色**：初见自带，允许随机与未知感，相对稳定。
- **相处习惯**：随共同经历与熟悉程度逐渐成长，形成与你特有的互动与表达。
- **当下情绪**：短期变化，为日常表现提供起伏，不直接等同于长期性格被改写。

普通互动允许不完全配合，例如躲开逗弄或表现自己的喜好；具体表现仍待设计。Herdr Agent 状态变化通知是必须履行的能力，不受这类自主性影响。

### 必需通知与角色表达

角色表达可以丰富，通知是否发生不能由宠物性格或模型自由决定。如何在模型暂不可用、动作中断、多 Agent 同时变化，以及连接断开和恢复时维持通知，是后续切片需要验证的要求；此处未冻结工程实现。

当前接受多气泡并行排队与逐渐消散；macOS 系统通知和声音是否作为额外渠道尚未指定。必须明确让用户感知状态变化，同时遵守不抢焦点、不影响操作的要求。不得以此前“偶发互动不能频繁”为由自行取消工作状态通知；频繁状态变化怎样清楚呈现需另行设计。

前期事件恢复实验显示断档期间的历史变化可能无法补回。产品要求仍保留为必需通知，后续须明确可观察事件、断连提示与恢复对账的边界，不能把恢复当前快照冒充所有历史变化均已通知。

## Coding Agent 发现、授权与会话分析

现行方向：Bayper 自动探索并发现可用的各家 Coding Agent，将对应的会话目录识别为候选数据来源。它仍通过 Herdr 感知 Agent 工作状态，但内容分析来源不再限定为 Herdr 中选定的项目或会话。具体支持哪些 Coding Agent、怎样发现可用性及定位会话目录，尚待技术核实。

已明确的用户控制：

1. 外部会话分析默认关闭。发现 Agent 不代表可以读取其会话正文或开始分析。
2. 用户可在 Bayper 设置页开启该功能；对发现的可用 Coding Agent，明确请求访问其对应会话目录，说明分析用途。开启功能不替代目录访问授权。
3. 获得对应授权后，才可将该目录中的会话内容用于构筑初步了解、记忆、偏好及有关经历；未授权时不分析对应目录。
4. API Key 的首次强制配置与外部会话分析的可选启用、目录授权是独立要求，配置 Key 不代表同意分析 Coding Agent 会话。

持续分析的更新时机、历史深度、授权说明与拒绝后的提示方式、开关关闭或撤销授权后如何处理已有记忆，以及模型接收原文还是筛选信息，仍待细化。授权要求不得被 Codex 的 master 调度权限或自动发现能力替代。

### 数据来源与记忆的关系

用户直接与 Bayper 的沟通、双方互动经历、经授权的 Coding Agent 会话内容，均可以成为记忆来源。外部目录保存的是来源数据，Bayper 需要独立维护提炼出的了解与记忆；具体存储载体和工程方案尚未确定。外部分析关闭不等于整个 Bayper 记忆能力关闭，直接沟通的记忆管理方式仍需细化。

用户已明确分析结果是可修正的初步了解，后续通过相处修正，不因一次任务固定偏好；明确纠正须及时更新。以下是 Codex 提出的具体整理原则，分类与历史表达方式仍待讨论：

- **明确表达与推测分开**：会话中明确说明的偏好，与仅从某次任务推测出的倾向保留区别。
- **工作背景可更新**：当前项目、任务与工具可提供当下话题，后续经历可以修正早先的判断。
- **过去背景与共同经历分开**：分析相识前的记录可以帮助了解背景，但不能冒称宠物当时亲自参与。分析到的内容如何与之后真正共处的经历联系起来，留待细化。

本轮修订记录：用户明确替换前版 REQ-12/13 的“用户选定项目或会话范围”方案，现以自动发现 Coding Agent、默认关闭分析、设置启用及会话目录明确授权为准；不保留旧方案作为并行配置要求。

- **模型服务**：为个性表现提供能力；它与日常动作、真实工作状态的职责边界待定。

2. 多个流浪宠物的日常共处：在住名额、临时/永久离开、与用户及彼此的关系、传承和新入住，以及自主互动的程度。
3. 连接与 Herdr 关系：按连接器类型/实例细化自动关联、去重与恢复，确认 Agent 独立身份，按本轮多气泡队列调整呈现，核对同屏容量与保留时效的冲突，并细化通知表达者接续；Herdr 多 server 细节留在其连接器内。
4. 模型服务使用边界：Coding Agent 发现与会话目录访问的授权体验、历史深度、外发信息、记忆管理、首次强制 Key 配置的完成条件、调用开销及使用中服务异常时的体验。
5. 根据前述决定形成首版核心范围、全局生命周期和体验判断，再选择开发切片。

## 记忆存储技术研究入口

用户明确区分技术存储与记忆方案：SQLite 便于本地存储，但不意味着记忆提炼、组织、修正、成长与遗忘的方案已确定，这些仍需继续研究。独立存储探针不属于 Bayper 正式开发，实验中的明确 ID 修订等规则只用于验证数据库行为，不直接升级为产品记忆规则。

用户提出 SQLite FTS5 + BM25 作为候选，并要求调研代表性实践。结果见 [记忆存储研究](memory-research.md)。当前建议优先验证 SQLite 记忆记录 + FTS5/BM25，语义召回有明确缺口时再考虑混合检索；这是 Codex 的技术研究建议，完整记忆方案尚未冻结；存储组成部分已有独立实测，边界见下文。重要偏好、明确纠正、性格底色与必需通知规则不能依赖一次关键词检索是否命中。

独立存储验证已完成，见 [SQLite 实测结果](sqlite-spike-results.md)；同义召回与自动记忆规则仍未解决，不将该探针作为正式记忆方案。

当前技术探索方向：用户要求停止第三方记忆产品的测试，倾向吸收经验、独立研究轻量本地方案。参见 [记忆产品参考与停止记录](memory-products-notes.md)。不将成熟框架集成或自研记忆架构冻结为本轮已实现能力。
