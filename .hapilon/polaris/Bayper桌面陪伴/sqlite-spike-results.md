# SQLite FTS5 + BM25 独立实测结果

2026-10-25。对应固定 [技术合同](sqlite-spike-cases.md)。用户授权构造数据、Claude Code 实现、Codex 独立审查运行并清理；不进入正式开发。用户特别澄清：SQLite 是方便的技术存储候选，记忆方案和规则仍要继续探索。

## 结论

本轮真实磁盘数据库支持现行记录、FTS 与修订审计的一致更新；明确纠正后，旧内容退出有效 get/search，重开与重建索引也不会重新生效。失败事务可以一起回滚正文、版本、索引与审计。

原文 unicode61 与 trigram 都未召回两字“安静”；有限字符 token 对照能检索一字、两字与连续短语，但不具备中文语义能力。“保持安静”与“别来烦我”不能自动相互召回，人工 OR 展开才能同时取回两条。SQLite/BM25 适合作为存储与检索的可验证组成部分，不能凭本轮判定它已解决产品记忆。

## 环境与真实执行

- macOS 27.0.1 arm64；Python 3.13.3 链接 SQLite **3.49.2**。最终探针使用这个运行时，Python optimize=0，assert 未被关闭。
- 独立读库额外使用系统 SQLite CLI **3.54.0**；不把它与 Python 链接版本混记。
- Claude Code CLI 2.1.310，会话 `6f1d1d79-299e-47a4-9864-4cea257dd582`。日志确认读取 AGENTS.md、CLAUDE.md、实验合同；全部代码由 CLI 实施，Codex 未代改。
- 最终代码：`research/sqlite-spike/store.py` 165 行、`probe.py` 314 行，共 479 行。高于约 250–350 行预期，增加部分是逐 Case 独立断言、证据字段及可读 SQL，无框架和新依赖；没有再压行换取指标。
- Codex 首轮独立执行通过；审查后返修，再在新的临时磁盘根独立运行最终版，通过 SQL-01..06。随后用只读 CLI 绕过 Python wrapper 检查当前记录、FTS、审计及 integrity_check。

## 审查、失败与返修记录

初版 CLI 自检使用 `python3 -I` 导致同目录 store 无法导入，后改用正常运行方式；曾对 BM25 结果误用插入顺序断言，已改为集合断言，排序本身由 SQL-03 独立检查。相关自检输出仍在原 CLI trace，不覆写失败。

Codex 首轮独立运行已通过，随后发现部分 SQL 为压行变得拥挤、字符范围用难辨认的直接字符、短语命中断言过宽且缺 trigram 阳性对照。交回 Claude Code 恢复排版与转义字面量，改为确切 ID 集合，并增加英文/大小写和三字 trigram 对照；最终独立重跑全部固定 Case 通过。没有削弱原文短词漏召回与同义漏召回预期。
