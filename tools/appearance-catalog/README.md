# Bayper 造型元数据库

建立日期：2026-10-25。用途：PRD 阶段的角色造型资料与制作依据。用户要求整个人形的参数级拆解，而非只列物种、猫耳或服装标签。这里是设计资料库，不是运行时捏人编辑器，也不是 Bayper 的记忆数据库。

当前画风基准唯一为 `bayper.pixel.maid10`：用户选定本工具 `references/style-board-02-maid.png` 的 **10号**，后续素材沿用其精细二次元像素效果、细密纹理和紧凑头身比例。选择画风与比例不表示该格的黑发、金瞳、服饰都必须成为所有角色的固定属性。产品选择依据见[第二轮记录](../../.hapilon/polaris/Bayper桌面陪伴/style-exploration-maid.md)，运行工具不依赖该文档。

## 自包含目录与对外能力

```text
tools/appearance-catalog/
├── README.md                 # 来源、语义、编辑与使用说明
├── build.py                  # 唯一建库入口
├── data/
│   ├── *.csv                 # 8份编辑源
│   └── catalog.sqlite        # 可读取的派生快照
└── references/
    └── style-board-02-maid.png
```

本工具拥有的脚本、数据、参考图与说明均在本目录维护；没有指向 PRD 的软链或旧目录 fallback。对外提供两项能力：通过 `build.py` 校验并重建资料快照，通过 `data/catalog.sqlite` 读取造型字典、候选、配方和设计依据。调用者不需拼接内部脚本。CSV 中的参考图路径以 `data/` 为根基解析，README 中的路径以工具根目录为基准。

整个目录复制到其他位置后仍应可独立构建，保留相对结构即可。PRD 只记录产品决定并引用本工具；发现、入住、记忆等产品规则不混入工具运行数据。

## 调研结论与采用依据

“造型元数据库”是本项目的命名，不能说成业界已有统一数据库标准。以下成熟工具分别提供了可借鉴的组织方法；本资料库是 Codex 对这些方法的综合与像素项目适配，不是直接复制某个工具的参数表，也未统计市场占有率。

| 一手资料 | 已核实的做法 | Bayper 的采用与边界 |
| --- | --- | --- |
| [VRoid 面部编辑](https://vroid.pixiv.help/hc/en-us/articles/4406164546969-How-to-edit-faces) | 面部区分虹膜、高光、眼白、眉、眼睑、眼线、睫毛、鼻、口等，部分要素可改位置、尺寸和颜色 | 借鉴细分形态与色彩；不引入其3D编辑器 |
| [VRoid 发型组合](https://vroid.pixiv.help/hc/en-us/articles/4405086656153-How-to-model-hair-easily) | 前发、后发与整体发型之外，还区分侧发、延长发、呆毛和附加部分 | 发型按结构与局部参数组织，不只有“长发/短发” |
| [VRoid 服装叠穿](https://vroid.pixiv.help/hc/en-us/articles/4405497325721-How-do-I-overlay-outfits) | 服装可组合多个模板，并各自调整参数与纹理 | 区分裁片、层次、外轮廓与材质；不假定所有层次任意兼容 |

| [Live2D 素材分离](https://docs.live2d.com/en/cubism-editor-manual/divide-the-material/) | 按眼睫等部位分离，补画运动后露出的遮挡区域 | 用于说明概念拆分不等于现成部件；没有选用 Live2D，也不照搬其越细越好的制作成本 |

## 资料的组织层次

1. **画风规范**：像素表现、头身比例和质量基准。跨角色、跨主题延续。
2. **参数维度**：形态、位置、比例、颜色、结构与表现规则，回答“可以描述和调整什么”。
3. **要素候选**：给参数的可读候选值，例如侧分刘海、猫尾、圆瞳；有描述不代表已有图片。
4. **角色配方与设计主次**：先指定主题约束和少量重点元素，再让其余维度围绕重点协调，形成可追溯的角色制作规格；不要求逐项手填310个值，也不逐项独立随机补齐。
5. **素材与兼容记录**：实际源文件、方向/动作覆盖、锚点、可替换范围和审查状态。只有完成制作与检查才算可用。
6. **主题应用**：引用上述候选、配方与素材，限定组合与内容批次。用户本轮要求先不展开主题细节，已有“首批女仆系列”决定保持。
7. **运行个体**：引用已发布外观版本，并拥有自己的身份、性格、记忆和关系。不会因为素材配方相同就成为同一个个体。

第6、7层目前只有关系说明，没有抢先创建主题或入住功能表。设计上有配方来源，不表示 Bayper 运行时生成图片；新角色美术仍在制作阶段完成，随版本加入。

## 主题、重点元素与整体协调

用户明确：设计一只 Bayper 不会强调所有维度；先构造若干关键特征，其他维度依据主题元素自动协调形成。这里的“自动协调”是制作阶段由 Codex/设计工具结合参考与约束完成设计，不是运行时生成图片，也不是本工具已实现数值求解。

建议按以下顺序使用资料库：

1. 继承10号画风与头身基准，明确主题语义与设计意图。
2. 选出少量真正决定识别度的重点元素，并说明哪些特征必须保留、哪些关系允许变化。
3. 其余头发、服饰、色板、材质、饰物与姿态围绕重点协调，不要求人逐项指定，也不把候选逐个随机相乘。
4. 出现冲突时调整协调元素；如果仍无法兼容，再显式修订重点，不偷偷让设计工具改掉角色识别特征或用户选定画风。
5. 审查整体轮廓、视觉主次、色彩与动作一致性，再将确定的结果固化为版本化配方。没有被强调不等于必须省略，也不等于每次重新生成时都可随意改变。

`design_guidance` 为既有10号参考形象补了10条示例记录。`design_role` 分为“画风固定”“重点元素”“协调元素”“待标定”；猫耳、围裙与发箍作为该参考的重点，是 Codex 对样张的解读，不冒充用户额外确认。设计重点可能映射多个维度，本表只是解释与追溯，不限制艺术构思只能沿一列变化。

例如，重点若是某种耳部轮廓与服装结构，发型会让出耳部空间、头饰避开耳根，色彩帮助读出服装层次，鞋与站姿延续整体重心。这些协调结果一旦确定就是该角色的稳定组成，不需全部提升为用户强调项。

## 参数语义：不把细致写成假精确

- `enum`：离散类型，`reference_basis` 中用分号列出初始候选。后续可增候选，不自动视为已制作。
- `ratio`：相对比例，分母逐行注明；不是统一的0～100。头身比为全身高度/头部高度；全身高度的身体量测不含兽耳、飘发、帽饰和鞋跟，头部高度不含发量与兽耳，需统一中立参考视图。当前图是比较样张，尚无准确量测，不编造实际比值。
- `position`：宿主部位的局部坐标；正视参考左上为原点，x向右、y向下，可用0～1描述，再在正式画布标定为逻辑像素。旋转、侧背视需要自己的参考，不拿四分之三投影冒充正视量测。左右按角色自身解剖侧记录。
- `angle`：以逐行声明的轴为基准，单位度；二维正视图正向按顺时针理解，侧背视另注明，不能混用。没有标定的值保持未知。
- `pixel`：正式素材的逻辑像素，不是比较图像素或屏幕 Retina 像素。未选独立角色画布前，不写假定的128px角色高或1px线宽为确认事实。
- `count`：非负整数；某部件不存在时不激活其子参数。`ordinal` 是有顺序的描述，不是假装连续精度。
- `color_role`：先记录语义色角色及其所处部位，精确色值和明暗色阶留给正式色板；不把“黑紫”当成已测量的 HEX。
- `time` / `rate`：动作表现的时间或频率，不是静态造型维度的随机值，不与动画图像帧数混淆。
- `record`：重复或结构化的设计描述，当前以文字保存，结构成员见下表；不是可执行表达式，也不是允许随意省略细节的“其他”。未来是否拆关联表要等制作需求，不在本轮实现通用参数引擎。

每个正式制作参数还需要记录：参考视图/版本、标定方式、设计允许范围、有效依赖、左右作用域、实际可见性和审核结论。概念设计中，未强调项可按主题与重点协调形成，不要求先有手填数字；正式导出所需精确数值或被遮挡结构仍须标定，不能将“已协调”冒充“已量测”。未知不等于0。

这些维度共同描述一个有主次的整体设计。例如眼部神态需要眼角、眼睑与眉势协调，肢体与衣袖围绕整体比例适配。数据库记录这种关系与结果，不要求用户理解独立自由度、逐项调滑杆或手工穷举参数；本工具不自动执行形变或审美求解。

## 像素下怎样实现这些参数

`pixel_policy` 是 Codex 的初步判断，不是实测可见性：

- **锁定参考**：沿用10号风格与比例；主题不能覆盖。
- **可见**：优先用实际尺寸验证轮廓、面部或色块差异。
- **联动**：不能独立抽样，受整体比例、宿主或其他参数约束。
- **细节限定**：小尺寸可能合并或省略；仍保留设计描述，不承诺独立滑杆。
- **侧视/背视限定**：必须新增对应参考才能标定，不因现在看不到就杜撰。
- **表情/动作限定**：需要对应帧和覆盖检查，不从静态图推断可用。

捏脸工具里的连续 morph 数值不能直接等价成像素图的连续变形；把一张位图横向拉伸也不能证明五官参数化已实现。建议近期用这些参数指导**制作阶段**的角色规格、提示词与复验，先以完整角色图集交付；局部换装或拼装只在真实部件兼容后采用，不预设运行时换装功能。

## 配方、兼容、主题与素材的边界

每个配方引用画风和明确参数，重要识别特征在后续方向与动作间保持。兼容不是单一标签：需要同时核对体型、像素网格、投影、锚点、色板、遮挡、动作/方向覆盖。纸面上有48个候选并不意味着存在48项素材，更不能用候选数量相乘宣称有若干万只可用角色。

`constraints.csv` 的23条规则是人工制作检查；当前脚本只检查引用有效，不执行碰撞、审美或动画判定。状态应逐步区分文字候选、概念参考、制作中、实际播放已审查、随版本发布。只有最后一层可以进入运行时相遇池；目前没有已发布记录。

主题属于应用层：它可以选择衣物/材质/配色、约束若干部件、组织一批角色；不能重新定义头身或像素画法，也不能按服饰强制套一种性格。角色配方、主题归属、现实用户偏好、运行个体和记忆分别保存概念归属，不做“同衣服等于同人格”的推断。

## 使用、重建与核对

在仓库根目录运行 `python3 tools/appearance-catalog/build.py` 重建快照。也可从任意工作目录使用绝对脚本路径；`--output <独立路径>` 用于复建检查。脚本仅构建这份设计资料库，正式存储方案未选定。

用 SQLite 客户端打开 `data/catalog.sqlite` 可按 `group_name` 查维度，按 `dimension_id` 查候选/配方，按 `design_guidance` 查看设计主次和协调依据。库不包含真实会话、用户偏好、API Key 或宠物记忆。
